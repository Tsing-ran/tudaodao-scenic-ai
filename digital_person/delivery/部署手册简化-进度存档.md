1. **主线定成什么？** 倾向：主线 = 现在的「档位 B + C 合并」，即一台带 GPU 的公网机上跑全栈；「无 GPU 快速体验」退成附录。**但要先确认用户是否同意砍掉档位 A 的主线地位**——档位 A 是唯一实测过的路径，且它承载了「准确率 ≥90% 红线」的验证，不能真删掉，只能挪位置。
2. **能不能因此把 `deploy.sh` 做成一条命令通吃？** 现在 `deploy.sh` 只管档位 A。若前提是「必有 GPU」，`deploy.sh` 就该自己 `nvidia-smi` 探测 → 有 GPU 就把档位 B 的 8 个步骤（conda/拉引擎/打补丁/编译 TRT/cuDNN8/底板/RTMP 绑定/SRS）全部沉进脚本里自动做完。**这才是手册能再砍一半的关键**——现在档位 B 的 8 步之所以在手册里，是因为没人把它们脚本化。
3. **公网那部分（档位 C）需要用户先答一个问题**：评委的公网机是什么形态？裸机 + 公网 IP（那就是 nginx + 证书）还是云平台代理（那就是把桥接层监听到被映射的端口）？两者步骤完全不同。**这个不问清楚会写错。**

**注意别踩的坑**：新前提**不能反过来削弱已验证的东西**。`bash deploy.sh` 是目前唯一端到端实测过的路径（见下方「实测结论」），档位 B 依然**从未验证过**且已知缺 3 个生产改动。「简化」不等于「把没验证的东西提到主线还说得很确定」。

### 实测中发现并修掉的 3 个真 bug（都会让评委卡住）

1. **`deploy.sh` 建虚拟环境失败**：`python3-venv` 是 Debian 系的独立包，缺了就 `ensurepip is not available`。我原来的预检 `python3 -m venv --help` 是**假阳性**（帮助信息照出，建的时候才炸）→ 改用 `import ensurepip` 实检 + root 下自动 apt 安装。
2. **`ops/quickstart_a.sh` 把 stderr 永久吞掉**：`port_busy` 写成 `... && { exec 3>&- 2>/dev/null; ...}`——**`exec` 不带命令时，重定向会永久作用于当前 shell**。一旦探到端口被占，后面所有 `dp_die` 的报错全静默，评委只看到「退出码 1，零解释」。已 A/B 实证（旧写法报错消失、新写法出现）并修复。
3. **`ops/stop_a.sh` 会杀掉同机上的其它部署**：只按 `pgrep -f "uvicorn backend.main:app"` 匹配 → **我实际把生产的 rag+bridge 杀了**（supervisor 12s 自动拉回，livetalking 未受影响）。已加 `_belongs_to_bundle()`（查 `/proc/<pid>/exe` 与 `cwd` 是否在包内）→ 回归实证：生产 PID 671719/671706 前后完全一致，脚本打印「跳过 pid 671706（不属于本源码包）」。

另修：**`.env.example` 的 `DEPLOY_MODE` 原本是 `local`** → 评委照手册跑会掉进 local 模式（下 2.2GB BGE-M3 + 吃显存）。已改 `cloud` 并验证 `deploy_mode = cloud`。
