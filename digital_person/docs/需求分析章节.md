# 第 2 章　需求分析

> 本章把赛题要求拆解为可验证的需求条目：先概述赛题与硬性指标（2.1），再按**用户角色**
> 展开用例（2.2），继而给出**功能性需求**（2.3）与**非功能性需求**（2.4）的逐条对照——
> 每条需求都标注其在本系统中的**实现载体**（接口/模块），形成"需求 → 实现"的可追溯矩阵；
> 最后以统一的"**预期输入 → 预期输出**"契约定义各算法模块的需求边界（2.5）。

---

## 2.1　赛题需求概述

本课题为第十五届中国软件杯 A 组赛题"**景区导览服务 AI 数字人**"（出题企业：锐捷网络），
要求面向景区游客与管理方构建 AI 数字人导览系统，并以**灵山胜境 + 拈花湾**为示范景区
提供公开资料包（游览指南、景点结构化数据集、14 万行游客行为数据）。

赛题的核心要求可归纳为三层：

1. **游客交互层**：支持语音与文本输入，数字人以语音、表情、口型同步的方式回答；
   提供历史、文化、景点特色的智能问答与个性化路线推荐。
2. **管理层**：知识库上传/更新/维护，数字人形象（外观/声音）配置，游客感受度报告，
   数据大屏概览。
3. **质量层（评审红线）**：问答准确率 **≥ 90%**（唯一带数值的硬性指标）；交互响应延迟
   控制在合理范围（赛题以"语音问答延迟 < 5 秒"为例）；口型同步与表情自然；
   **至少使用 1 个多模态大模型**；系统稳定不崩溃。

此外，本系统自加一条**架构级约束**（源自赛题"知识库管理"要求的深层含义，也是本设计的
灵魂）：**系统不绑定任何特定景区**——导入任意景区的知识库后，问答准确率须同样达标。

## 2.2　用户角色与用例分析

系统服务两类角色，其用例全景见**图 2-1 系统用例图**（`docs/diagrams/07_用例图.png`）。

| 角色 | 描述 | 使用环境（实际形态） |
|---|---|---|
| **游客** | 在景区游览过程中寻求讲解、问路、推荐与帮助的个人 | 手机浏览器网页（iOS Safari 走 HLS、安卓 Chrome 走 FLV）；规划中的安卓 APK |
| **景区管理方** | 负责景区运营、内容维护与服务质量监控的工作人员 | 桌面端网页（含数据大屏） |

**游客侧用例**（8 项）：文本提问、语音提问、拍照视觉定位、听个性化讲解（按同行人格
差异化）、获取路线推荐（含错峰建议）、情绪安抚关怀、被主动迎宾、查看行程游记。

**管理侧用例**（5 项）：知识库管理（上传/更新/删除）、数字人形象配置（外观/音色）、
查看数据大屏、查看游客感受度报告、接收负面情绪/突发预警。

典型场景串联（与演示叙事线一致）：游客打开页面 → 数字人**主动迎宾**自我介绍 →
游客拍摄大佛照片 → 系统**视觉定位**"您正在大佛广场"并接地讲解 → 游客带孩子，
系统以**亲子人格**讲故事并提示母婴设施 → 询问路线时结合**实时客流与天气**给出
错峰建议 → 游览结束生成**电子游记**；全程对话情绪入库，管理方在大屏看到
热点话题与情感趋势，负面情绪触发**预警**。

## 2.3　功能性需求

按角色编号（FR-T = 游客端，FR-M = 管理端），每条标注实现载体——这同时是
"需求→实现"追溯矩阵：

### 游客端

| 编号 | 需求描述 | 实现载体 |
|---|---|---|
| FR-T1 | 文本提问，获得基于景区知识库的准确回答 | `POST /chat`（同步 + SSE 流式） |
| FR-T2 | 语音提问：录音自动断句、转写为文字后进入问答 | 前端能量 VAD + `POST /asr`（faster-whisper，~1.1s/句） |
| FR-T3 | 数字人以语音+口型同步+表情回答，回答与情绪联动 | LiveTalking/Ditto 实时全脸驱动（约 25fps）+ 情绪韵律与原生表情条件按 `[情绪:X]` 热切换 |
| FR-T4 | 拍照视觉定位：拍摄景物 → 识别所在位置 → 接地讲解与指路 | `POST /chat/image` 两段式（qwen-vl 认地标 → RAG 接地生成） |
| FR-T5 | 个性化讲解：按同行关系切换叙事人格 | `group_type` 参数（成人/亲子/老年/情侣 四种人格指令） |
| FR-T6 | 个性化路线推荐，结合实时客流与天气给出错峰/避雨建议 | navigation/recommend 意图 + `crowd.py`（14万行真实行为数据）+ `env_context.py`（wttr.in 天气） |
| FR-T7 | 多语言问答：自动跟随提问语言或强制指定 | `lang` 参数（auto/zh/en/ja/ko/fr/de/es/ru，共 9 档） |
| FR-T8 | 主动迎宾：连接后数字人主动打招呼、自我介绍、邀请互动 | `GET /trip/greeting`（按景区导游名+人格差异化） |
| FR-T9 | 行程总结：生成本次游览的温暖游记回顾 | `GET /trip/summary`（引用会话史含拍照定位点） |
| FR-T10 | 情绪安抚：识别游客负面情绪并给予关怀回应 | empathy 意图路由 + 共情指令 |

### 管理端

| 编号 | 需求描述 | 实现载体 |
|---|---|---|
| FR-M1 | 知识库上传、查询、删除；上传后即时生效 | `POST /kb/upload`、`GET /kb/list`、`DELETE /kb/{id}`（入库自动失效答案缓存与实体索引） |
| FR-M2 | 多景区知识库隔离：新增景区不影响既有景区 | ChromaDB 多 collection 命名空间（`scenic_{id}`） |
| FR-M3 | 数字人形象配置：按景区配置外观与音色 | `GET/PUT /digital-human/config`；AI 换装生成链路（ComfyUI + InstantID 锁脸换装） |
| FR-M4 | 数据大屏：会话量、热点话题、情感趋势可视化 | `GET /analytics/dashboard`、`hot-topics`、`sentiment-trend` |
| FR-M5 | 游客感受度报告：基于会话数据自动生成 | `POST /analytics/report`（LLM 生成） |
| FR-M6 | 负面情绪预警与知识盲区发现 | `GET /analytics/alerts`、`GET /analytics/knowledge-gaps` |

## 2.4　非功能性需求（对照评审红线）

每条 NFR 给出**实测值**，数据来源为第 4 章的可复现评测（`tests/eval_run.py` 等）：

| 编号 | 需求 | 指标要求 | 实测值 | 结论 |
|---|---|---|---|---|
| NFR-1 | 问答准确率 | ≥ 90%（硬性红线） | **97.1%**（105 题严格自动评分；人工复核 100%；5 景区分别 94.3~100%） | ✅ |
| NFR-2 | 语音问答响应延迟 | 合理范围（赛题例：<5s） | 端到端（说完→数字人开口）≈ **3.8s**＝VAD 0.8 + ASR 1.0 + RAG 首句 1.8(p95) + TTS 首块 0.7 + 渲染首帧 0.3 | ✅ |
| NFR-3 | 多模态大模型 | ≥ 1 个 | qwen-vl-max（视觉定位）+ qwen-plus（文本），多模态语料闭环 | ✅ |
| NFR-4 | 口型同步与表情自然 | 专家评估 | Ditto 实时全脸驱动（约 25fps、首帧约 0.7s）口型同步；驱动源肖像本人、神态自然；情绪韵律与原生表情条件热切换 | 演示视频呈现 |
| NFR-5 | 抗幻觉/可信度 | （自加强化） | 陷阱题拒答纠错 **100%**（15/15）；EA-RAG 置信度门控经标定（库外拒答 60%、零误拒） | ✅ |
| NFR-6 | 景区无关性（插拔式） | 换库后仍达标 | 5 个景区（灵山/拈花湾/西湖/黄山/故宫）全部 ≥90%，新景区仅需上传文档 | ✅ |
| NFR-7 | 稳定性 | 不崩溃、无长时无响应 | AutoDL supervisor 进程守护，进程退出自动重启（实测约 8s 自愈）；数字人显存占用约 2.7GB | ✅ |
| NFR-8 | 端兼容性 | 手机可用 | iOS Safari（HLS）与安卓 Chrome（HTTP-FLV）双路自适配；麦克风经 HTTPS 隧道授权 | ✅ |

> **关于 NFR-2 的口径说明**：赛题原文将"<5 秒"作为"合理范围"的**示例**而非硬性定值
> （唯一带数值的硬指标是准确率）。本系统仍将其当作工程目标对标，并采用对体验最严格的
> 端到端口径（游客说完最后一个字 → 数字人开口）。其中"首句开口"由逐句流式架构保证：
> 答案边生成边播报，整段时长不影响感知延迟（详见第 4 章）。

## 2.5　算法需求（预期输入 / 预期输出契约）

各算法模块以统一契约定义需求边界——这是后端与前端、队友间协作的接口依据：

**① RAG 智能问答**
- 预期输入：`{session_id, message, scenic_id, group_type?, lang?, stream?}`
- 预期输出：`{reply（口语化、无Markdown）, emotion（6类）, intent（5类）, sources, context_used}`；流式时按 `intent → emotion → sentence×N → end` 事件序下发
- 质量约束：准确率 ≥90%；知识库无答案时必须兜底拒答，不得编造

**② 意图分类（多智能体路由）**
- 预期输入：`query + 对话历史`
- 预期输出：`qa / navigation / recommend / empathy / chitchat` 五选一
- 质量约束：高频问题规则命中 0ms；分类失败安全回退 qa

**③ 多模态视觉定位**
- 预期输入：`景物照片（base64）+ 可选文字问题 + scenic_id`
- 预期输出：`{location（识别出的景点位置或 null）, reply（接地讲解与指路）}`
- 质量约束：地标识别置信不足时不得武断定位，转为通用讲解并引导

**④ 语音识别（ASR）**
- 预期输入：16kHz 单声道音频（WAV/WebM）
- 预期输出：中文文本（含景区专名纠错）
- 质量约束：单句转写 ≤1.5s；生僻专名（九龙灌浴、梵宫）正确率优先

**⑤ 语音合成与数字人驱动**
- 预期输入：`文本句 + emotion + scenic_id（决定音色）`
- 预期输出：音频流 + 30fps 口型同步视频流（RTMP→SRS→FLV/HLS）
- 质量约束：句级驱动（首句即开口）；情绪切换在句间安全点原子生效

**⑥ 客流感知**
- 预期输入：`scenic_id + 当前时间`
- 预期输出：拥挤档位（空闲/适中/较多/繁忙）+ 旺淡季 + 错峰时段建议
- 质量约束：基于真实行为数据（14 万行）的统计模型；数据缺失时优雅降级不阻塞主流程

**⑦ 情感分析与运营报告**
- 预期输入：会话记录（含 emotion 标注）
- 预期输出：大屏指标（热点话题/情感趋势）、感受度报告、负面预警、知识盲区清单
- 质量约束：异步统计，不增加问答链路延迟

## 2.6　本章小结

本章将赛题要求落为 **16 条功能性需求**（全部有实现载体可追溯）与 **8 条非功能性需求**
（其中 7 条已有实测数据支撑），并以 IO 契约固化了 7 个算法模块的边界。其中
**NFR-6 景区无关性**是贯穿全文的设计主线——它把"做一个灵山的导览"升格为
"做一个任意景区可即插即用的导览平台"，后续章节的架构与算法设计均围绕此展开。
