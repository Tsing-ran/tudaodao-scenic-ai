## 三、生产端流水线提速攻坚（2026-07-12，本次，完整过程记录）

### 3.1 背景与现象

游客大屏端（9:16 竖版直播路）数字人说话呈机械节奏卡顿："说三到五个字卡约 1 秒，循环往复"；
同期另发现说话时唇形压塌成一条线（见 3.6）。环境：AutoDL RTX 4090 D（24G），
双路 LiveTalking + Ditto 常驻（主路 16:9 640×360 供手机端、竖版路 9:16 720×1280 供大屏）。

### 3.2 瓶颈定位：逐层排除

方法学（可复用）：
1. **源头/播放端分离**：ffmpeg 直录 SRS 源头流 → `silencedetect` 分析音频空洞；浏览器端
   AudioContext 录制页面实际出声对比。源头干净而播放端有洞 = 播放链路问题，反之为生成端。
2. **真实产帧率**：SRS API `/api/v1/streams/` 帧计数间隔 20s 两采差分（比 tqdm 日志准确）。
3. **组件裸基准**：可疑组件单独压测（如推流编码器空转测吞吐）。
4. **逐段埋点**：流水线每个 worker 包一层计时，每 300 帧打印平均毫秒。

排除过程与数据：

| # | 假设 | 实验 | 数据 | 结论 |
|---|---|---|---|---|
| 1 | 网络中继丢包 | 源头直录 32s + silencedetect | 语音段内仅 0.33~0.70s 停顿、位置=标点，与逗号/句号数一致 | 排除（属 TTS 韵律停顿，正常）|
| 2 | TTS 供给不足 | 日志时序分析 | 单句合成 1.4s、对应播放 ~4s，队列始终充足 | 排除 |
| 3 | 软编码过慢 | rtmp 推流器裸编基准 | 720×1280=94.1fps(10.6ms/帧)、640×360=146.8fps | 排除 |
| 4 | **产帧不足** | SRS 帧计数差分（20s） | 竖版 18.8/s、主路 21.7/s，标称 25；GPU util 98% | **命中**：流比实时慢 ~25%，播放器周期性耗干缓冲回补 ≈ 每播 4s 停 1s |

卡顿节奏的成因闭环：生产端每秒只产出 0.75~0.87 秒的音视频 → 任何播放器的缓冲以固定速率
亏空 → 周期性停顿回补，且与网络无关（网络越好越规律）。

### 3.3 措施一：TensorRT 引擎原生重编（Ampere 兼容版 → Ada 原生）

发现：现役引擎为官方预编译 `ditto_trt_Ampere_Plus`（硬件兼容模式），在 4090 D（Ada）上
非最优。从官方 ONNX（2.5GB，14 个模型）重编原生引擎，fp16 + builder-optimization-level 5。

踩坑记录（写"实现中的问题与解决"小节的素材）：
- 官方转换脚本在算力 ≥8.0 的卡上会**自动加回** `--hardware-compatibility-level=Ampere_Plus`，
  照抄命令会编出与原来无异的兼容引擎，需改脚本禁用（含 warp_network 的 python-API 分支）；
- 转换依赖 polygraphy 未随环境安装；`os.system` 调用要求其在 PATH。

效果：GPU 利用率 98% → 68%（两路合计），但竖版路帧率 19.05 → 19.15/s **几乎不变**——
证明 GPU 算力已不是吞吐瓶颈，瓶颈在流水线组织（引出措施三）。主路 21.7 → 24.4/s。

### 3.4 措施二：putback 合成 ROI 化

逐段埋点数据（竖版路，措施一后）：

| 阶段 | 线程 | 平均耗时 (ms/帧) | 说明 |
|---|---|---|---|
| stitch | GPU | 4.1 | 运动拼接 |
| warp | GPU | 14.0 | 特征体扭曲 |
| decode | GPU | 24.4 | SPADE 解码 512×512 |
| putback | CPU | **19.4** | 512 人脸区贴回 720×1280 底图 |
| writer | CPU | ~0 | 编码推流（异步内部缓冲）|

putback 原实现对整幅 720×1280 做 warpAffine + 混合，但 mask 只覆盖人脸 warp 区域
（约 1/4 面积），区外像素与底图完全相同。改为 ROI 内运算 + 整帧拷贝：
**19.4 → 11.1 ms/帧**。帧率 19.15 → 19.95/s（小幅）。

### 3.5 措施三：TRT 每模型独立 CUDA 流（决定性一刀）

对照实验先行：临时停主路，竖版路独占 GPU 仅 21.2/s → 排除进程间争抢，瓶颈在**单进程内部**。

代码审查发现：TRT 封装 `infer(stream=0)`——所有模型共用默认流，同进程 4 个 GPU 阶段
（stitch/warp/decode/lmdm）虽在不同线程，GPU 上完全串行，理论上限 = 各段之和
(4+14+24≈42ms→24fps)，叠加线程气泡实际只有 19~21fps。

改动：每个 TRT 模型实例创建独立非阻塞 CUDA 流，H2D/执行/D2H 全排本流、调用末尾同步本流
（对调用者仍是同步语义，上下游时序不变）。安全性论证：跨阶段传递的 GPU 张量每帧全新分配
（warp 输出 `torch.empty` 新张量），无跨帧缓冲复用 → 无写后读竞态。

效果：不同帧可在不同阶段并行，吞吐上限从"各段之和"变为"最慢单段"。

### 3.6 伴生问题：唇形坍塌（底图平移禁忌）

现象：说话全程嘴唇压扁成一条线甚至一个点，完全不张开（逐帧截图 24 帧无一张嘴）。

判定实验（单变量对照）：同一形象、同一台词，
- 磁盘底图 = 前一日"批量水平重居中"的平移图 → 唇形坍塌；
- 恢复未平移原图（其余全部不变）→ 张嘴露齿完全正常。

结论：**Ditto 底图 PNG 不允许事后平移/重构人物位置**——运行中引擎持有的驱动模板与
图错位，嘴部 warp 落在错误区域。处理：275 张底图全量回滚原图，生成管线的自动居中禁用
（居中改由生图 prompt 约束承担）。

教训（可写入"实现中的问题与解决"）：对推理引擎的输入资产做"看似无害"的几何变换前，
必须先做单资产对照实验再批量执行。

### 3.7 总效果对照（绘图主数据表）

帧率（SRS 帧计数差分，/s）：

| 阶段 | 竖版路 9:16 | 主路 16:9 | GPU util |
|---|---|---|---|
| 基线（Ampere 兼容引擎） | 18.8 | 21.7 | 98% |
| + 原生 Ada 引擎 | 19.2 | 24.4 | 68% |
| + putback ROI | 20.0 | 24.4 | 68% |
| + 每模型独立 CUDA 流 | **27 计数/s（达标）** | **24.9** | 67~75% |
| 说话负载下复测 | 27.3 持续 | 24.8 | 67% |

音频完整性（silencedetect / volumedetect）：

| 采样点 | 结果 |
|---|---|
| 源头流（AutoDL SRS） | 仅存 0.3~0.8s 标点韵律停顿，无异常空洞 |
| 中继后（杭州 ECS） | 同源头，SRT 链路零劣化 |
| 源头音量 主路/竖版 | max -8.8dB / -9.4dB（健康语音电平）|
| 浏览器页面实录 | max -8.2dB，触摸解除静音后正常出声 |
