# 并发与成本规模化设计

> 总体设计文档章节稿。主题：在保证「每位游客都能获得 <5s 及时的数字人答复」的前提下，
> 把单位服务成本压到**远低于真人导游**。本章遵循「痛点 → 理念 → 架构 → 原理 → 数据 → 落地 → 边界」的论证范式。

---

## 1 问题的提出：从"会说话的展品"到"人人可用的导游"

一个能在演示里流畅对答的数字人，离一个**能真正投放景区**的产品，隔着三道现实拷问：

- **痛点一·并发**：景区是「成百上千游客各自掏手机」的高并发场景，不是单路演示。
- **痛点二·实时**：导游的价值在「问完即答」，端到端延迟必须 <5s，且高峰不能卡。
- **痛点三·成本**：若每个在线游客都独占一块 GPU 做实时渲染，成本将**线性爆炸**，反而比真人导游更贵——产品在商业上不成立。

本章给出的方案，要同时满足这三条：**人人可用、人人及时、成本碾压真人导游**。

---

## 2 问题分解：两类并发，难度差一个数量级

系统的并发被清晰地切成两半，扩展难度天差地别：

| | 逻辑后端并发（问答/分析/配置） | 数字人渲染并发（口型/表情实时生成） |
|---|---|---|
| 资源 | CPU + 网络 I/O（等 LLM/嵌入返回） | **GPU 算力 + 显存** |
| 扩展性 | 易：无状态，多 worker + 负载均衡水平扩 | 难：每路实时渲染独占 GPU |
| 单卡承载 | 单进程异步可扛数百并发 I/O | 一张 4080(12G) ≈ **1–2 路** |
| 瓶颈 | SQLite 写锁（换 PostgreSQL 即解） | **GPU 是硬天花板** |

**核心矛盾在右列**。设朴素方案为"每个在线游客全程独占一路渲染"：

$$
\text{所需 GPU 数} = \frac{\text{在线游客数}}{1\!\sim\!2}
$$

1000 个在线游客 ≈ 需 500–1000 张 GPU。这正是成本爆炸的根源，**必须从架构上击穿这个假设**。

---

## 3 核心设计理念：GPU 按「发话瞬间」共享，而非「会话」独占

关键观察——游客的交互是**稀疏突发**的：

> 问一句 → 数字人说 10–20 秒 → 然后走路 / 看景 / 拍照 1–2 分钟 → 才问下一句。

也就是说，**GPU 只在"正在说话的那十几秒"被需要，其余时间完全空闲**。朴素方案的错误，是为每个游客的"整段逗留"占着 GPU，而真正的占用率（duty cycle）极低：

$$
\text{占用率} = \frac{\text{单次说话时长}}{\text{两次提问间隔}} \approx \frac{15\text{s}}{120\text{s}} \approx 12.5\%
$$

把模型从「**按会话独占**」改为「**按发话共享**」——发话时占用一个渲染槽、说完立即释放给下一个游客——一块 GPU 的服务人数即可放大约 **1/12.5% ≈ 8 倍**，叠加缓存后更高。这与"餐厅不给每位客人配一个全职厨师、而是厨师按菜单出菜"是同一种统计复用思想。

---

## 4 架构：三层漏斗

请求按"成本由低到高"逐层下沉，绝大多数请求在前两层被低成本消化，最后一层做安全兜底，保证**任何请求都不会卡死**：

```
                          游客提问
                             │
        ┌────────────────────┼─────────────────────┐
        ▼                    ▼                       ▼
  ① 高频问答缓存        ② GPU 池(按发话调度)        ③ 满载降级兜底
  命中→播预渲染视频      抢到空闲渲染槽→实时驱动      无槽/数字人离线
  0 GPU·0 LLM·<0.5s     占1路·说完即放·<5s开口      →先秒回文字/语音答
        │                    │                       │
   吃掉大部分请求        长尾/个性化问答            突发高峰·绝不卡
        └────────────────────┴───────────────────────┘
                             │
                       人人 <5s 得到答复
```

### 4.1 L1 — 高频问答视频缓存（最大成本杀手）
景区问答高度重复（"大佛多高""门票多少""厕所在哪"——长尾极度集中）。将 Top-N 高频问答**离线预渲染成数字人视频片段**并缓存，命中即直接播放成品视频：**0 GPU、0 LLM、<0.5s**。系统已有文本答案 LRU 缓存（实测命中 0.03s），L1 是其"视频版"。迎宾、固定景点讲解、路线介绍等**固定内容全部预渲染**，常态零实时 GPU。命中率越高，均摊成本越趋近于 0。

**已实现**：清单 `webapp/public/faq/manifest.json`（每条问答含触发短语 `match`/答案/情绪/`clip`）；桥接 `/live/ask` 入口先做归一化子串匹配，命中即短路返回 `{mode:"clip", clip_url, cached:true}`——**不调 RAG、不占渲染槽**；前端在舞台直接播该成品视频、播完回归。预渲染脚本 `scripts/prerender_faq.py`（在 GPU box 上：ffmpeg 抓 SRS 流 + `/live/say` 驱动 → 截成 mp4 → 回写清单 → 调 `/live/faq/reload` 热生效）。**实测命中 0.001–0.004s，对比走 RAG 8.9s——快约 2000–9000 倍且零 GPU/LLM 成本。**

### 4.2 L2 — GPU 池 + 按发话调度
M 块 GPU 组成渲染池。游客发话 → 抢占一个空闲渲染槽 → 复用既有「**首句抢跑**」流式机制（RAG 出第一句即送渲染、<5s 开口）→ 说完后槽位**按估算说话时长自动释放**，立即被下一个游客的发话复用。由 §3 的稀疏性，一块 GPU 实测可服务约 **50–80 游客/小时**（朴素独占模式仅 1–2 人）。

> **调度算法详见 [`docs/L2多GPU池调度算法设计.md`](L2多GPU池调度算法设计.md)**：分发用「一致性哈希有界负载(CHBL，保 avatar 亲和省冷启动) + Power-of-Two-Choices(防热点)」，容量用 Erlang-C/M-G-c 精算（算例显示 L1 缓存 50% 命中可把所需 GPU 数从 ~20 砍到 ~10），伸缩用**客流数据预测式预热**——并诚实指出实时数字人**不能跨用户拼批**（增益来自时分复用非批处理，与 LLM serving 的本质区别）。

### 4.3 L3 — 满载降级兜底（保证"人人"）
突发大客流占满 GPU 池、或数字人服务离线时，该条请求**自动降级为纯文字/语音答复**：答案照常秒回（逻辑后端高并发零压力），只是这一条没有"会动的脸"。产品 80% 的价值（问答 / 路线 / 定位 / 游记）**不依赖实时渲染**，降级近乎无感。**这一层是"绝不让任何游客等不到答复"的安全垫。**

## 5 关键机制与实现（已落地部分）

L3 与 L2 的容量调度**已在桥接层（`bridge/server.py`）落地并实测**：

- **渲染容量池 `AvatarPool`**：以"槽位"建模 GPU 并发。`try_acquire()` 非阻塞抢槽，`release_after(估算说话时长)` 在说完后异步释放——直接实现「按发话占用、说完复用」。池大小由环境变量 `AVATAR_POOL_SIZE` 配置（本地单卡=1，GPU 池部署时按卡数设）。
- **容量决策**：`/live/ask` 在驱动前判断「LiveTalking 可用 **且** 抢到槽位」→ 驱动数字人；否则**不驱动、只收集文字**，返回 `mode:"text", degraded:true, degrade_reason`（`pool_full` / `livetalking_down`）。答案永远返回。
- **观测**：`GET /live/capacity` 暴露 `{pool_size, in_use, available, livetalking_ok}`，供运维与数据大屏监控负载。
- **流式基元**：L2 复用既有的「首句抢跑」（桥接订阅 RAG 句子级 SSE，每出一句立即驱动），这是"边渲染边播放、压住 <5s"的关键。
- **前端协同**：游客端读 `degraded` 标志，降级时展示「💬 文字模式·繁忙」提示，UX 诚实不欺。

## 6 性能与成本：用数据说话

### 6.1 延迟（实测，满足 <5s）
| 环节 | 延迟 | 测法 |
|---|---|---|
| 软件链路（问完→数字人收到开口驱动）| 冷 2.28s / 热均 **1.61s** / 缓存 0.03s | mock 打点实测 |
| Qwen-TTS 首音 | **0.35s** | qwen3-tts-flash-realtime 流式首包实测 |
| MuseTalk 首帧 + 推流缓冲 | ~0.2s + ~0.8s(FLV) | 架构估值 |
| **端到端（文字+FLV）** | **≈ 3.0s（冷 3.6s）** | ✅ <5s 有余量 |

> latency-critical 主干（软件 1.61s + TTS 0.35s = 1.96s）实测明确 <5s。

### 6.2 降级容量（实测，保证人人及时）
池=1 时**两个游客同时提问**：一个驱动数字人（`mode=avatar`），一个自动降级文字（`mode=text, reason=pool_full`）——**两人都拿到答案、无人阻塞或报错**。数字人离线时同样稳定降级（`reason=livetalking_down`），答案照出。

### 6.3 成本测算 vs 真人导游
| | 真人导游 | 数字人方案 |
|---|---|---|
| 服务模式 | 1 人带 1 团(~20–30人)，不能 1 对 1 | **1 对 1、无限并发**（弹性扩池）|
| 时长/语言 | 8h、单语 | **24h、多语言、不知疲倦** |
| 单位成本 | 导游 ¥300–500/天 ÷ ~20 人 = **¥15–25/人** | **< ¥1/游客**（见下）|

数字人单游客成本（按逗留 3h、问 10 次估）：
- L1 缓存命中部分 ≈ **¥0**（播成品视频）；
- L2 实时渲染：云 GPU ¥3–6/小时 ÷ ~80 游客/小时 ≈ **¥0.05–0.08/游客**；
- LLM+TTS（DashScope）：~¥0.3–0.5/游客；
- **合计 < ¥1/游客 —— 比真人导游人均低一个数量级以上**，且 1 对 1 / 24h / 多语言 / 可弹性无限并发。

## 8 诚实的边界与风险

- **当前 GPU 池实测为单槽（pool=1）**：完整多 GPU 调度与弹性伸缩属规模化阶段工程，本章已落地的是「容量抽象 + 降级floor」，多卡只需调 `AVATAR_POOL_SIZE` 并接 GPU worker。
- **缓存命中率是成本的关键变量**：景区问题重复率高使命中率乐观，但需上线后用真实 `analytics/hot-topics` 数据持续校准预渲染清单。
- **降级文字答复的"首字延迟"**：当前 `/live/ask` 在降级时返回整段 JSON（非流式），文字模式感知延迟≈整答时长；可后续让文字模式直连流式 `/chat` 进一步压低。
- **HLS(iOS) 分段缓冲**比 FLV 高 1–3s，是端到端延迟的变量，需真机校准。

---

### 结语
本方案以「**GPU 按发话共享 + 高频内容预渲染缓存 + 满载降级兜底**」三层漏斗，把"每位游客独占一块 GPU"的不可承受成本，转化为"少量 GPU 服务大量稀疏发话 + 大部分请求零成本缓存命中"。在**保证人人 <5s 及时答复**（降级永不卡）的同时，将单游客成本压到 **< ¥1**，实现对真人导游的**成本碾压**——这是本产品从"能演示"走向"可规模化运营"的关键支撑。
