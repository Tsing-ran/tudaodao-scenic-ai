# 多智能体调度与同行人格切换 — 设计说明

> 本文档说明「途叨叨」两大核心机制的设计思路与实现，供总体设计文档、答辩与队友对接使用。
> 一句话立意：**从被动问答机器人，到主动陪伴型导游。**

---

## 一、为什么需要这两个机制

市面同类方案普遍是"单体大模型 + RAG + TTS + 2D 数字人"的线性堆叠，本质是一个**被动应答的问答机**：不管游客问什么，都走同一条链路、用同一种口吻回答。

但真实景区是**移动、多情境、多角色**的场景：

- 游客的诉求是分类型的——有人问知识，有人要路线，有人在抱怨，有人只是闲聊；
- 同一段历史，讲给学者、讲给带娃家庭、讲给老人、讲给情侣，方式应当截然不同。

因此我们引入两个机制：

| 机制 | 解决的问题 | 对应创新点 |
|---|---|---|
| **多智能体 Orchestrator** | 让系统**懂分工**：不同诉求走不同处理逻辑 | 核心创新一 |
| **同行人格切换** | 让系统**懂情境**：同样内容因人而异地讲 | 核心创新二 |

---

## 二、多智能体 Orchestrator（意图分派）

### 2.1 为什么不是单体大模型

把"问答、路线、推荐、安抚、闲聊"全塞进一个超长 prompt 会带来三个工程问题：

1. **指令互相干扰**，模型顾此失彼，准确率下降；
2. **难以针对单一能力做精细优化与评测**，一处调整牵动全局；
3. **无法弹性伸缩**——所有请求都打到同一个重型模型，浪费且变慢。

我们的做法是在 RAG 流水线**入口**加一层轻量"导诊台"——Orchestrator，先判断意图，再路由到对应的处理逻辑。

### 2.2 混合分派策略：规则快筛 + LLM 兜底

意图识别如果每次都调一次大模型，会给最高频的"知识问答"凭空增加 ~150ms 延迟。因此采用**两级混合策略**：

```
游客提问
   │
   ▼
① 规则快筛（关键词命中）──────► 命中 → 直接路由（0ms）
   │ 未命中
   ▼
② 是否模糊？(短问题 + 有上下文)
   │ 是                          │ 否
   ▼                             ▼
③ LLM 兜底分类(qwen-turbo)     默认 qa（知识问答）
```

- **绝大多数请求走规则，0ms**，不给主链路添延迟；
- 只有"规则没命中且本身模糊"（如带指代的短追问）才调用一次轻量模型；
- LLM 分类失败时**安全回退到 qa**，绝不崩溃。

### 2.3 五类意图与差异化处理

| 意图 | 触发示例 | 处理策略 |
|---|---|---|
| `qa` 知识问答 | "灵山大佛多高" | 走原有 RAG 链路（**完全不改动，保住 97.1% 准确率**） |
| `navigation` 路线规划 | "半天怎么逛" | 注入路线规划指令：给出顺序、停留时间、景点衔接 |
| `recommend` 个性推荐 | "有什么适合拍照的" | 注入推荐指令：推荐 2-4 项并说明理由 |
| `empathy` 情感安抚 | "排队太久了好烦" | 注入安抚指令：先共情再帮助，情绪优先[情绪:关切] |
| `chitchat` 闲聊 | "你叫什么名字" | 亲切回应，**跳过 RAG 检索**省延迟 |

实现方式：每类意图对应一段"任务指令"，在构造 system prompt 时注入（与原有的语言指令同一机制），**同一套 LLM 链路即可输出差异化回应**，无需为每个 Agent 部署独立模型。

### 2.4 对数字人驱动端的输出（SSE 事件）

流式接口在 LLM 调用前就能下发意图，新增 `intent` 事件，排在最前：

```
event: intent    data: {"type":"intent","value":"navigation","label":"路线规划"}
event: emotion   data: {"type":"emotion","value":"happy"}
event: sentence  data: {"type":"sentence","text":"...","index":0}
event: end       data: {"type":"end","full_text":"..."}
```

事件顺序：**intent（最早）→ emotion（首 token 后）→ sentence… → end**。
前端可用 `intent` 实时展示"当前意图"，也可忽略（向后兼容）。

### 2.5 代码位置

```
backend/agent/
  intents.py        # Intent 枚举 + 关键词规则表（快筛层）
  orchestrator.py   # classify()：规则命中即返回，模糊才 LLM 兜底
  handlers.py       # 每类意图的任务指令 + 闲聊跳过检索判断
```

接入点：`backend/rag/pipeline.py` 的 `answer()` / `answer_stream()` 入口。
`qa` 分支原样调用既有逻辑，**对核心准确率零影响**。

## 三、同行人格切换（情境感知）

### 3.1 设计理念

> 同样一段历史，讲给学者、讲给情侣、讲给带娃家庭，方式应当截然不同。

"个性化推荐"不应只是标签过滤，而应是**千人千面、有温度**的叙事差异。系统通过 `group_type` 参数感知同行关系，切换叙事人格。

### 3.2 四种人格

| group_type | 同行关系 | 叙事风格要点 |
|---|---|---|
| `adult`（默认） | 通用成人 | 标准热情导游，无额外约束 |
| `family_kids` | 亲子家庭 | 讲故事、拟人化、互动提问（"小朋友猜猜看～"）、提示亲子设施/母婴室 |
| `senior` | 老年长辈 | 放慢节奏、句子简短、强调无障碍/休息座椅/医疗点/缓坡，避免推荐爬山久站 |
| `couple` | 情侣出游 | 浪漫意境、推荐合影机位/私密角落/祈福点/日落观景处 |

### 3.3 实测效果（同一问题"灵山有什么好玩的"）

- **亲子**："可多啦！…小朋友猜猜看，为什么是九条龙给佛祖沐浴呀？…特别适合拍照打卡"
- **老年**："适合慢慢观赏的地方…可以坐在广场边的长椅上…这里地势平坦，您可以慢慢走"
- **情侣**："亲爱的…傍晚时分你们可以手牵手漫步…摸摸佛掌祈福，寓意沾福气、保平安"

一个参数，三种截然不同、各有温度的讲解。

### 3.4 实现机制

- 与意图指令、语言指令一样，人格作为一段"叙事人格指令"注入 system prompt；
- `adult` 或未知值返回空指令（默认人格），**安全降级**；
- **缓存隔离**：答案缓存键升级为 `group_type::lang::query`，避免不同人格/语言间串答。

### 3.5 代码位置

```
backend/llm/prompts.py
  GROUP_LABELS              # group_type → 中文名
  _build_persona_directive  # 生成人格指令，adult/未知 → 空串
  build_system_prompt       # 新增 group_type 参数
```

接口入口：`POST /chat` 请求体新增 `group_type` 字段（默认 `adult`，向后兼容）。

## 四、工程考量

- **延迟**：意图分派绝大多数 0ms；闲聊跳过检索；保持 < 5s 端到端红线。
- **不破坏核心**：`qa` 链路与既有逻辑完全一致，97.1% 准确率不受影响。
- **可扩展**：新增意图 = 加一条规则 + 一段指令；新增人格 = 加一条指令。无需改动主链路。
- **可答辩**：`orchestrator.py` 是真实可见的分派代码，可现场演示同一数字人对五类诉求、四种人格的差异化响应。

## 五、对赛题评分项的对应

| 评分维度 | 本设计的支撑点 |
|---|---|
| 数字人技术集成度 | 多 Agent 架构 + intent/emotion 事件驱动表情与叙事 |
| 大模型与知识库准确性 | qa 链路零改动，保住 97.1%；意图分派减少 prompt 干扰 |
| 行业实用与体验性 | 路线/推荐/安抚差异化处理 + 千人千面人格切换 |
| 交互自然度与用户体验 | 同一问题因人而异地讲，有温度的主动陪伴 |
