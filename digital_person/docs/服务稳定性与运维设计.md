# 服务稳定性与运维设计

本章说明系统在演示与试运行阶段如何保证服务稳定性，包括进程守护、一键启停、演示前自检三部分，以及实施过程中定位并解决的若干工程问题。

## 1. 背景与目标

数字人导览系统由六个常驻服务组成（媒体服务器 SRS、两路实时数字人引擎 LiveTalking、RAG 问答后端、桥接层、北京到杭州的推流中继），分布在一台带 GPU 的服务器上。早期这些服务靠手工脚本逐个后台拉起，存在三个稳定性隐患：

1. 进程非常驻。任一服务因异常退出，或服务器实例重启后，进程全部丢失，需要人工逐个重新拉起，期间服务中断。
2. 缺少统一的健康观测手段。演示前无法快速确认全栈是否就绪，存在临场翻车风险。
3. 启动顺序与依赖靠人记忆维护，容易出错。

赛题对非功能性指标的要求是“系统稳定，不应崩溃或长时间无响应”。本设计的目标是：服务进程在意外退出后自动恢复，提供一键启停与一键体检，把“能演示”提升到“稳定可演示”。

## 2. 部署环境约束

实施方案前先确认了运行环境的两个关键约束，它们直接决定了技术选型。

第一，运行环境是容器，1 号进程是 bash，没有以 systemd 作为 init。因此无法使用 systemd 管理服务，改用 supervisor。supervisor 是用户态进程管理器，以普通进程身份运行，能够监控子进程存活并在其退出时自动重启，恰好满足需求。

第二，该 GPU 与其它任务（模型训练、图像生成）共用。因此进程守护不能在开机或登录时自动抢占 GPU，否则会干扰其它任务。设计上把数字人栈的启动权交给运维人员，通过一条命令显式拉起，supervisor 只负责“拉起之后保活”；另提供一键全停命令，随时把 GPU 让给其它任务。

## 3. 进程守护设计

用一份 supervisor 配置统一托管六个服务，核心策略如下。

自动重启。每个服务设置 `autorestart=true`，进程意外退出后由 supervisor 自动拉起。这是补齐“进程非常驻”缺口的关键。

启动顺序。用优先级控制启动次序：SRS 媒体服务器最先（其余服务向它推流或从它拉流），随后是 RAG、两路 LiveTalking、桥接层，中继最后。

存活判定与重启退避。GPU 引擎进程秒级即存活，但真正出流约需 85 秒，因此“存活判定时长”按进程存活设置（20 秒），出流就绪由后续体检脚本查 SRS 推流状态确认，两者解耦。

干净停止。每个服务设置 `stopasgroup` 与 `killasgroup`，停止时连同其派生的子进程（例如中继的 ffmpeg）一起回收，确保 GPU 显存真正释放、端口不残留。

自动重启的效果经过实测验证：手动以 `kill -9` 杀掉 RAG 进程模拟崩溃，supervisor 在约 8 秒内以新进程号将其重新拉起，健康检查随即恢复。

## 4. 一键启停

在 supervisor 之上封装两个运维脚本。

启动脚本 `dp_up.sh`：若 supervisor 未运行则启动它，由它按配置自启并保活全部服务；若已运行则确保所有服务处于启动状态。开机后只需运行这一条命令。

停止脚本 `dp_down.sh`：停止全部服务与 supervisor 本体，并打印残留的 GPU 计算进程供核对，把 GPU 让给其它任务。

## 5. 演示前自检

体检脚本 `preflight.sh` 在演示前一次性核验全栈状态，关键项全部通过才开始录制。检查覆盖六个方面：

1. 进程守护：六个服务是否全部处于 RUNNING。
2. 端口监听：七个关键端口（RAG、桥接、两路引擎、SRS 的 RTMP 与 API 与 HTTP-FLV）是否在监听。
3. 接口健康：RAG 与桥接层的健康端点是否返回正常。
4. 直播双流：SRS 上两路数字人推流是否均为 active。
5. GPU 占用：是否有对应的引擎计算进程在用 GPU。
6. 公网可达：公网网关的代理健康端点是否可达。

另提供 `--audio` 选项，驱动数字人说一句话，抓取直播流 8 秒做电平检测，确认数字人确实发出清晰语音而非静音。实测一次完整体检为 15 项全部通过，其中语音平均电平约 -30 dB（清晰语音，静音通常在 -90 dB 量级）。

## 6. 工程问题与解法

实施过程中定位并解决了四个具体问题，记录如下。

第一，supervisor 对相对命令路径的解析基准。SRS 原启动命令用相对路径 `./objs/srs`，配进 supervisor 后报找不到命令。原因是 supervisor 按自身工作目录解析命令可执行文件，而非按服务配置的 `directory`。解法是命令用绝对路径，`directory` 仍保留用于运行时解析配置文件的相对路径。

第二，启动顺序竞态导致推流未建立。首次启动时 SRS 因上述路径问题反复退避了约 40 秒，期间两路 LiveTalking 已经起来并向尚未就绪的 SRS 推流，结果推流连接建立但 publish 状态为非活跃、无帧流动。SRS 稳定后重启两路引擎即重建推流恢复正常。根治手段是优先级排序保证 SRS 先起，叠加引擎侧已有的推流看门狗在 SRS 异常时自动重连。

第三，容器内缺少 `ss` 命令。体检脚本最初用 `ss` 查端口监听，但该容器即便在登录 shell 下也没有 `ss`，导致端口检查全部误报。改用 bash 内建的 `/dev/tcp` 直连探测，对 RTMP 与 HTTP 端口同样适用，且零外部依赖。

第四，音频电平检测取不到数值。volumedetect 的平均与峰值电平是以 info 级别输出的日志，脚本最初用 `-loglevel error` 恰好把这两行过滤掉；同时对实时分块 FLV 流，时长参数 `-t` 放在输出侧会停滞，需放在输入侧限制读取时长。两处修正后电平检测稳定可用。

## 7. 稳定性边界与后续

当前方案补齐了“进程死了自动重启”这一最大缺口，并提供了可复现的启停与体检流程。仍存在的边界如实说明如下：受容器无 init 的限制，服务器实例重启后需要运维人员手动运行一次启动命令，supervisor 随后接管保活，这一步无法做到完全无人值守；当前为单实例部署，没有跨机故障转移。规模化部署阶段可引入多实例与负载均衡、以及外部进程编排来进一步提升可用性。
