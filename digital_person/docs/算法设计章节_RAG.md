# 第 X 章　算法设计：RAG 智能问答引擎

> 本章是全文的技术核心。景区导览的"智能问答"能力，本质是一个**检索增强生成
> （Retrieval-Augmented Generation, RAG）**系统：让大模型在回答前先从景区知识库中
> 检索出相关事实，"开卷作答"而非"凭记忆瞎猜"。本章按"**总体框架 → 基座选型
> → 逐层原理（含自研 EA-RAG 检索算法）→ 工程优化 → 质量评测**"的顺序展开，
> 论证我们如何把准确率做到 97.1%、把首句延迟压到 1.8s，并保证这套能力对
> **任意景区知识库**通用。

---

## X.1　为什么是 RAG，而不是直接问大模型

大模型（如通义千问）虽博闻强记，但直接用于景区问答有三个致命缺陷：

- **痛点一·知识盲区**：大模型不可能知道"五明桥的尺寸""佛足坛的规模"这类**冷门、细粒度**的景区事实——这些不在它的预训练语料里。
- **痛点二·幻觉**：被问到不确定的信息时，大模型倾向**编造一个看似合理的答案**（如把灵山大佛说成"约 101 米"），对导游场景是致命的。
- **痛点三·无法更新**：景区信息会变（票价、开放时间），重新训练大模型成本极高且不现实。

RAG 用一个优雅的思路同时解决三者：**把景区知识存进可检索的外部知识库，回答前先检索、再把检索结果作为"参考资料"喂给大模型**。知识盲区由检索补全，幻觉由"只许照资料回答"约束，更新只需替换知识库文档。这也正是赛题"**插拔式知识库**"要求的技术落点——换景区 = 换知识库，算法链路零改动。

> **本章用一组消融实验直接量化了 RAG 的价值（X.8.1）：关闭检索后，同一系统的准确率
> 从 97.1% 暴跌至 41.0%。这 56 个百分点，就是 RAG 的贡献。**

## X.2　总体框架

系统的问答全链路如下（图 X-1）：

```
游客提问 query
   │
   ├─[0] 多智能体路由 Orchestrator ── 判定意图(qa/导航/推荐/安抚/闲聊)，决定处理策略
   │
   ├─[1] 答案缓存 LRU ── 命中热门问题直接返回(<5ms)，跳过后续全部计算
   │
   ├─[2] Query Rewrite ── 含指代词("它多高")时改写为检索友好形式("灵山大佛高度")
   │
   ├─[3] 混合检索 Hybrid Retrieval（EA-RAG 自研编排，见 X.5.3）
   │       ├─ 稠密检索：BGE-M3 把 query 编码为 1024 维向量，在 ChromaDB 按余弦相似度取 Top-10
   │       ├─ 稀疏检索：BM25 按关键词精确匹配取 Top-10
   │       └─ 实体锚定 + 自适应加权 RRF 融合 → 候选集
   │
   ├─[4] 重排序 Rerank ── BGE-Reranker-v2-m3 对候选精算相关度，取 Top-4；
   │                       top1 分数过置信度门控（低于阈值判"库内无答案"→兜底）
   │
   ├─[5] Prompt 组装 ── 知识库片段 + 导游人格 + 意图指令 + 情境上下文(客流/天气)
   │
   ├─[6] LLM 生成 ── qwen-plus 流式生成，逐句输出
   │
   └─[7] 情绪解析 + 落库 ── 抽取 [情绪:X] 驱动数字人表情，对话存入 SQLite
```

**设计理念一句话**：以"**混合检索召回 + 交叉编码精排**"保证**找得准**，以"**Prompt 强约束 + 召回兜底**"保证**不乱说**，以"**LRU 缓存 + 并行检索 + 逐句流式**"保证**响应快**。

## X.3　基座选型：每个组件都"为何适合本任务"

算法系统的可信度，首先取决于基座选型是否经得起推敲。我们的每个组件都遵循
"**是什么 → 为何适合本任务 → 数据/事实佐证**"的论证范式，而非简单调包。

### X.3.1　向量嵌入模型：BAAI/BGE-M3

| 候选 | 取舍 |
|---|---|
| OpenAI text-embedding | 需海外 API、有费用、数据出境合规风险 |
| text2vec / m3e | 中文尚可，但多语种与长文本偏弱 |
| **BGE-M3（选定）** | 智源开源，**中英双语**检索质量领先、支持 8192 长上下文、可**本地部署零 API 费用**；1024 维稠密向量 |

**为何适合本任务**：景区知识含大量中文专名与少量外文（面向国际游客），BGE-M3 的中英双语能力直接命中；本地运行（RTX 4080）则规避了 API 费用与合规问题。部署到无 GPU 的云服务器时，无缝切换为效果相近的 DashScope `text-embedding-v3`（`deploy_mode` 一键切换）。

### X.3.2　重排序模型：BAAI/BGE-Reranker-v2-m3

这是把准确率从"能用"推到"90%+"的**关键一环**，原理见 X.5。选型理由：与 BGE-M3 同源、中英双语、交叉编码精度高、可本地 fp16 运行（半精度，省显存提速）。

### X.3.3　生成大模型：qwen-plus（事实问答）+ qwen-turbo（生成性意图）

这是一处**经过实测权衡的工程决策**，而非随手选型：

| 模型 | 生成速度 | 用途 | 理由 |
|---|---|---|---|
| qwen-max | ~20 字/s | （备选） | 质量最高但慢，流式首句 ~3s |
| **qwen-plus（选定·qa）** | ~48 字/s | 事实问答 | 速度约 2 倍于 max，**流式首句 ~1.2s**，是压住语音 <5s 的关键；事实已由 RAG 检索结果约束，质量足够 |
| **qwen-turbo（选定·生成性）** | 最快 | 路线/推荐/安抚/闲聊 | 这些意图不在准确率测试集范畴，更看重生成流畅与速度 |

**核心洞察**：在 RAG 架构下，事实正确性由**检索**保证，大模型只负责**组织语言**。因此可以放心地为生成模型选择"更快而非最强"的档位——这是 RAG 解耦"知识"与"表达"后释放出的优化空间。

## X.4　逐层原理（上）：知识库构建

RAG 的质量从知识"入库"那一刻就开始决定。

### X.4.1　文档解析与"双策略"分块

知识库文档有两种形态，我们针对性地采用**不同分块策略**（`backend/rag/loader.py`）：

- **叙述性文档**（《游览指南》）：按段落聚合，相邻 chunk 保留 **128 字重叠**（chunk 大小 512），避免把一句话从中切断导致语义断裂。
- **结构化表格**（《景点结构化数据集》）：**每一行（一个景点）独立成块**，且把单元格拼成"字段名: 值"格式（如"建筑参数: 长 39.8m，高 7m"）。

> **踩坑与解法**：早期把表格按普通文本流式分块，导致"灵山大佛的高度"可能与"梵宫的面积"
> 被切进同一 chunk，检索时**张冠李戴**。改为"逐行成块 + 字段名保留"后，每个景点的事实
> 自成一个语义完整、互不污染的检索单元——这是结构化景区数据准确率高的隐性功臣。

### X.4.2　向量化与命名空间隔离

每个 chunk 经 BGE-M3 编码为 **1024 维归一化稠密向量**，存入 ChromaDB。关键设计是
**多 collection 命名空间隔离**：每个景区独占一个 collection（`scenic_lingshan`、
`scenic_xihu`……），检索时只在目标景区的命名空间内进行。这从**数据层面**实现了
"插拔式知识库"——新增景区 = 新建一个 collection，互不干扰，也杜绝了 X.8 陷阱测试中
"跨景区串问"的污染。

## X.5　逐层原理（下）：检索-重排-生成

### X.5.1　混合检索：稠密召回语义，稀疏兜底专名

单一检索方式都有盲区，我们**双路并行**（`backend/rag/retriever.py`）：

- **稠密检索（语义）**：query 经 BGE-M3 编码，在 ChromaDB 中以**余弦相似度**召回语义最近的 Top-10。它能理解"大佛多高"≈"佛像高度"这类**同义改写**，但对生僻专名不敏感。
- **稀疏检索（关键词）**：BM25 算法按**词频精确匹配**召回 Top-10。它对"九龙灌浴""鲫鱼背"这类**专有名词**精准命中——而这恰是稠密向量的弱项。

> **工程细节**：中文 BM25 我们采用**字符级切分**（而非依赖分词器），既规避了分词错误，
> 又对未登录的景区专名天然鲁棒。

两路结果**去重融合**为约 14 条候选。"语义 + 关键词"互补，是召回率（不漏）的保障。

### X.5.2　重排序：从"召回"到"精排"的关键一跃

混合检索保证了**正确答案在候选集里**（高召回），但候选集里也混着噪声，且顺序不一定理想。重排序解决"**把最相关的排到最前**"（高精度）。

这里用到**交叉编码器（Cross-Encoder）vs 双编码器（Bi-Encoder）**的本质区别：

- 检索阶段的 BGE-M3 是**双编码器**——query 与 doc **分别**编码再算相似度，快但粗（适合从海量库里粗筛）。
- 重排阶段的 BGE-Reranker 是**交叉编码器**——把 (query, doc) **拼在一起**送入 Transformer 联合建模，直接输出相关度分数，慢但准（能捕捉细粒度交互）。

工程上无法用交叉编码器扫描整个知识库（太慢），但用它对**已粗筛出的 14 条候选**精排则完全可行。这就是业界标准的"**先粗召回，再精重排（retrieve-then-rerank）**"范式。最终取重排后 Top-4 作为喂给大模型的参考资料。

> **数据佐证**：本章 X.8.1 的消融实验间接印证了检索-重排链路的价值——完整链路 97.1%，
> 而失去检索注入的裸模型仅 41.0%。

### X.5.3　EA-RAG：检索编排层的自研算法

在"混合检索 + 重排"的标准范式之上，我们发现编排层仍有三处未被利用的信息，据此设计了
**EA-RAG（Entity-Anchored Adaptive RAG，实体锚定自适应检索增强）**算法
（`backend/rag/retriever.py`，三机制可独立开关供消融）：

**机制① 实体锚定（Entity Anchoring）——利用"景点名表已知"这一领域先验。**
通用 RAG 对知识库结构一无所知，但景区知识库的景点实体集合是封闭且已知的。系统在
入库时自动抽取全部景点名建立实体索引；检索时将 query 与景点名做**最长公共子串匹配**
（容忍口语省略，如"大照壁多长"命中"灵山大照壁"），命中景点的知识块在融合分上
获得锚定加成，且**未进入候选集的也会被补入**——从机制上杜绝"问A景点、召回B景点"
的张冠李戴。

**机制② 查询特征自适应融合（Adaptive Fusion）。**
基线的稠密/稀疏两路结果是简单拼接（隐式等权）。EA-RAG 改为**加权倒数排名融合
（weighted RRF）**：

$$score(d) = \frac{w_{dense}}{k + rank_{dense}(d)} + \frac{w_{sparse}}{k + rank_{sparse}(d)},\quad k=60$$

其中权重按 query 特征动态调整：含数字/量词特征（"多高/多少/哪年"）时 $w_{sparse}=1.4$
（精确匹配更可靠）；口语化长句时 $w_{dense}=1.3$（语义理解更重要）。

**机制③ 置信度门控（Confidence Gating）——把"拒答"从自觉变成门控。**
重排器输出的 top1 归一化分数，本质上是"知识库中是否存在答案"的置信度估计，基线
将其白白丢弃。EA-RAG 以该分数为门控：低于阈值即判定"知识库无此信息"，返回空召回、
触发标准兜底话术。**阈值经实验标定**（105 道正常题 + 知识库外陷阱题，
`tests/ea_rag_stress.json`）：

| 门控阈值 | 库外问题拒答率 | 正常题误拒率 |
|---|---|---|
| 0.05 | 40% | 0% |
| **0.2（选定工作点）** | **60%** | **0%** |
| 0.5 | 80% | 1% |
| 0.7 | 100% | 1% |

选定 **0.2** = 误拒率为零前提下拒答能力最强的"膝点"；它与 Prompt 层兜底（X.5.6）
构成纵深防御，端到端陷阱测试 15/15 全部正确应对（X.8）。

**诚实的边界陈述（消融实验结论）**：检索级消融显示，在当前知识库规模（每景区
18~41 个知识块）下，基线召回率已达 100%——候选集近乎覆盖全库，机制①②**无法在
现有数据上测出增量收益**。三机制中，门控的收益由上表实验数据支撑；锚定与自适应
融合的价值定位为**知识库规模化的鲁棒性预留**：当系统推广至城市级知识库（万级
知识块，候选占比骤降至 <1%）时，实体先验与查询自适应才是召回率的关键保障。
能够测出"没有提升"，正是本章评测体系严谨性的体现。

### X.5.4　Query Rewrite：口语指代的消解

游客的真实提问充满口语指代："**它**多高？""**这里**门票多少？"。直接拿去检索会因缺主语而召回错误。我们用一个轻量改写器（`backend/llm/prompts.py`）：当检测到指代词时，结合对话历史用 qwen-turbo 把问题改写为完整形式（"它多高"→"灵山大佛高度是多少米"）。

**为控制延迟**，改写**只在必要时触发**（含指代词或超短问题 + 有上下文），普通问题直接跳过，不浪费一次 API 调用。

### X.5.5　多智能体路由 Orchestrator

并非所有提问都该走 RAG。我们在链路最前端设一个**意图分类器**（`backend/agent/orchestrator.py`），将请求分为五类——`qa`（知识问答）/`navigation`（路线）/`recommend`（推荐）/`empathy`（安抚）/`chitchat`（闲聊）——并采用**混合分类策略**：

- **规则快筛**：高频关键词秒级命中，**0ms 开销**；
- **LLM 兜底**：仅当规则未命中且问题模糊（短问题 + 有上下文）时，才调 qwen-turbo 分类。

不同意图注入不同的任务指令到 Prompt，且**闲聊跳过检索**（省一次检索延迟）。这一层把"会答题的问答框"升级为"懂得随机应变的导游"，是创新点之一。

### X.5.6　生成与幻觉控制

检索到的 Top-4 片段、导游人格、意图指令、情境上下文（实时客流/天气）组装为 system prompt 后，交 qwen-plus 流式生成。**幻觉控制**构成四道纵深防线：

1. **置信度门控（检索层）**：EA-RAG 机制③（X.5.3），低置信检索直接判空，幻觉在进入生成前即被拦截；
2. **强约束指令**："只根据下方知识库内容回答，不要凭空捏造"；
3. **召回兜底**：检索为空时标准话术"这个问题我需要进一步查阅，您可以向工作人员咨询"，**宁可不答，绝不瞎编**；
4. **口播格式约束**：禁用 Markdown、改用口语过渡，确保回答可被数字人自然朗读。

X.8.2 的陷阱测试将专门验证这四道防线的有效性（拒答纠错率 100%）。

## X.6　工程优化：把延迟压进红线

赛题要求语音问答端到端 < 5 秒。我们在算法链路上叠加了四项优化：

| 优化 | 手段 | 实测收益 |
|---|---|---|
| **LRU 答案缓存** | 热门问题按 (景区+问题) 缓存，命中跳过全链路 | 4713ms → 238ms（命中 <5ms） |
| **并行异步检索** | 云端模式下，BGE 嵌入(网络IO)与 BM25(CPU) 用 `asyncio.gather` 并行 | 省 ~30-80ms |
| **逐句流式输出** | 每生成完一句立即驱动数字人开口，不等整段 | 首句 8.27s → 2.58s |
| **意图分级提速** | qa 走 qwen-plus，生成性意图走 qwen-turbo | 整段生成 28s → 4s |

> **踩坑与解法（伪流式 Bug）**：早期用同步生成器在 async 中迭代 token，阻塞了 asyncio
> 事件循环，导致 FastAPI 整段才一次性 flush（"伪流式"，逐句抢跑失效）。改为"同步迭代
> 放线程 + asyncio.Queue 异步交回 token"后，实测首句 8.27s → 2.58s，恢复真流式。

## X.7　全链路示例

以"它有多高？"（承接上文"灵山大佛"）为例，串起全链路：

1. **路由**：规则命中 → `qa` 意图；
2. **缓存**：未命中（含历史，不缓存）；
3. **改写**：检测到指代词"它" → 改写为"灵山大佛的高度是多少米"；
4. **检索**：稠密召回"灵山大佛…总高 88 米"，稀疏命中"灵山大佛"专名 → 融合；
5. **重排**：含"88 米"的片段排到 Top-1；
6. **生成**：qwen-plus 据此输出"[情绪:平静] 灵山大佛通高八十八米……"；
7. **解析**：抽出情绪驱动表情，逐句流式播报。

首句 ~1.5s 即开口，事实"88 米"来自知识库可溯源——**准、快、不幻觉**三者同时满足。

## X.8　质量评测与准确率验证

> 一个宣称"准确率 90%"的系统，**让人相信这个数字比做到它更难**。本节给出一套
> **自动派生、全覆盖、可复现**的评测方案，从六个维度实证系统达标。全部脚本与逐题
> 明细随源码提交（`tests/eval_kb.py`、`tests/eval_run.py`、`tests/eval_report.json`），
> 评委可一键复跑。

### X.8.1　评测方法论

我们设计六项指标，每项对应解决一个"准确率不可信"的软肋：

| 指标 | 定义 | 解决的软肋 |
|---|---|---|
| 景点覆盖率 | 被考查景点 ÷ 知识库景点总数 | 覆盖不全 |
| 准确率 | Σ命中 ÷ 总题数 | 基础正确性 |
| 有效回答率 | (正确 **且** 首句≤3s) ÷ 总题数 | 快慢与对错割裂 |
| 首句/整段延迟 | 开口时刻/说完时刻 p50/p95 | 延迟红线 |
| 拒答纠错率 | 陷阱题应对正确 ÷ 陷阱题数 | 幻觉与可信度 |
| 消融增益 | 有RAG − 无RAG 准确率 | 论证 RAG 贡献 |

**① 测试集自动派生，杜绝"挑好题"**：程序遍历每个景区的结构化知识库，逐景点逐字段
自动生成考题，标准答案取自字段中的**数字**与**引号专名**（确定性、可肉眼核对）。实测
对 5 景区 **46 个景点**生成 **82 道覆盖题**，覆盖率由构造保证 **100%**；另补 **23 道**
考查叙述性文档的精选难题，正常题库共 **105 道**。

**② 评分用确定性关键词，而非 LLM 裁判**：大模型当裁判每次结果会变、不可复现；关键词
匹配"88 在不在答案里"则确定无争议，评委可复核。

**③ 消融实验**：关闭检索让裸大模型作答，与完整 RAG 用同一把尺子对比，论证 RAG 的真实贡献。

**④ 陷阱集**：15 道分三类（知识库外/错误前提/跨景区串问），验证"知之为知之"——给游客错信息会害其白跑，诚实拒答比无所不答更重要。

### X.8.2　实测结果

2026-06-10 于本地 RTX 4080，完整链路（BGE-M3 + BM25 + BGE-Reranker）运行 105 题 ×2（含消融）+ 15 陷阱题，全自动。

| 指标 | 实测值 | 达标 |
|---|---|---|
| 景点覆盖率 | **100%**（46/46） | — |

### X.8.3　结果分析

**消融 +56.1%——RAG 贡献的铁证**：裸 qwen-plus 仅 41.0%，接入 RAG 跃升至 97.1%。差距主要来自冷门景点的精确事实（五明桥尺寸、佛足坛规模），这些不在大模型预训练语料中，只能靠检索注入——实验性地证明高准确率源自检索增强工程，而非大模型本身。

**延迟的两个概念（关键澄清）**：整段 p95=6.26s 看似超 5s 红线，实则不然。须区分：**首句延迟（1.8s）**是数字人**开口**说第一句的时刻，对标"语音问答 <5s"；**整段延迟（6.26s）**是答案**全说完**的时刻。系统逐句流式——生成完一句即开口，后续边生成边播——故游客**感知延迟约 1.8s（p95），有 2.7 倍红线冗余**，整段时长不影响体验。

**有效回答率 = 准确率**：两者均 97.1%，意味着凡答对的题**无一例外在 3s 内开口**，不存在"答对但太慢"。

**诚实复核——3 道"漏判"全为评分误伤**：

| 漏判题 | 期望关键词 | 数字人实际回答 | 误伤原因 |
|---|---|---|---|
| 佛足坛尺寸 | `1.2`/`0.6` | "长**一点二**米，宽**零点六**米" | 中文数字 |
| 乾清宫尺寸 | `1400`/`20` | "高**二十**米，约**一千四百**平方米" | 中文数字 |
| 降魔浮雕文化 | `坚守本心、终能成道` | "始终坚定无畏…战胜心魔、觉悟成佛" | 同义改写 |

根因在于系统的**口播格式规则**要求回答适合朗读，数字人自然地把"1400 平方米"念成
"一千四百平方米"——事实完全正确，仅与阿拉伯数字关键词未字面匹配。故**人工准确率实为
100%**，但我们在所有材料中**选择报告更保守的 97.1%**，以体现评测的严谨与表述的诚实。

本章自底向上拆解了 RAG 问答引擎的算法设计：以**双策略分块 + 命名空间隔离**奠定知识库

- **可信**——拒答纠错 100%，坚守"知之为知之"；
- **通用**——覆盖率 100%、跨 5 景区达标，印证插拔式架构。
