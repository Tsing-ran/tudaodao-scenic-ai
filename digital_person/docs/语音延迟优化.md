# 语音问答端到端延迟优化（< 5 秒）

## 1 问题背景与优化目标

语音交互是本系统最核心、也最延迟敏感的体验：游客开口提问后，若数字人迟迟不应答，会立刻产生"卡顿""没反应"的负面观感；而数字人形象越写实，对"答非所时"的容忍度反而越低——长时间静止的写实人脸会落入"恐怖谷"，破坏导游的拟人感。因此，**让数字人"尽快开口"是自然度与体验的共同前提**。

赛题在非功能性需求中对此提出要求（原文）：

> 系统稳定，**交互响应延迟应控制在合理范围内（如语音问答延迟 < 5 秒）**，保证用户体验流畅；
> 稳定性：系统不应出现崩溃或长时间无响应。

需准确理解该指标的定位：它归属于**"系统稳定性 / 流畅体验"**这一非功能性维度，与"系统不应崩溃或长时间无响应"并列，本质诉求是"**响应及时、不卡顿、不假死**"。其中 **"< 5 秒"是赛题对"合理范围"给出的示例性说明（"如"），而非如准确率那样的硬性评定值**——对照之下，赛题对准确率的表述是"事实性问答的准确率**不低于 90%**，由评审专家基于标准测试集评测"，含明确数值、评测方式与"不低于"，是确定的硬红线；延迟一项则为"合理范围内"的体验性要求。

据此，我们将 **"语音问答延迟 < 5 秒"作为一个明确的自定工程目标**来对标，并主动收紧——既满足赛题对流畅体验的要求，也为现场网络抖动留出余量。需说明：赛题未定义"语音问答延迟"的度量边界，**本节采用的端到端口径（从用户说完到数字人开口）为我方自定义**，以便量化与优化。

经前期实测，未优化前我们的语音链路存在三类问题：

- **生成慢**：事实问答从用户说完到数字人开口需 4.4–7.6 秒，逼近甚至超出 5 秒目标；
- **冷启动尖峰**：导览/推荐类问题首次触发时偶发约 20 秒的"假死"，直接违背"不应长时间无响应"的稳定性要求；
- **感知延迟**：用户说完话后，系统要等待较长静音才判定"说完了"，凭空增加等待。

本节的优化目标：**在确保问答准确率 ≥ 90%（硬红线）的前提下，将语音问答端到端延迟稳定压到 5 秒以内并留有余量，同时彻底消除冷启动尖峰。**

## 2 延迟预算分解（五段流水线）

优化的第一步不是"调快某个环节"，而是把端到端延迟拆解为**可独立度量、独立优化的串行流水线**，再定位其中"最大且最可控"的一段集中突破。

语音问答的完整链路如图 2-1 所示：

```
用户说完
   │  ① VAD 判定语音结束
   ▼
 录音音频 ──② ASR 转文字──▶ 文本问题
   │
   ▼
 ③ RAG 检索（向量+关键词混合、重排）
   │
   ▼
 ④ LLM 流式生成（句子级）
   │
   ▼
 ⑤ TTS 合成 ──▶ ⑥ 数字人口型渲染 ──▶ 开口
```

**图 2-1　语音问答端到端流水线**

各段的初始耗时与责任归属如表 2-1。由于是串行链路，**总延迟 = 各段之和**，任一段超标都会拖累整体响应、影响流畅体验。

| 阶段 | 初始耗时 | 责任模块 | 是否本文优化对象 |
|---|---|---|---|
| ① VAD 静音判定 | 0.8 s | 前端 | ✅ |
| ② ASR 语音转文字 | ~1.0 s | 语音服务（Paraformer） | 否（已达标） |
| ③ RAG 检索 | 0.3–1.2 s | **RAG 后端** | ✅ |
| ④ LLM 首句生成 | **2.7–7.6 s** | **RAG 后端** | ✅（主战场） |
| ⑤ TTS 首块合成 | ~0.7 s | 语音服务（CosyVoice） | 已调查 |
| ⑥ 数字人首帧渲染 | ~0.3 s | LiveTalking（MuseTalk） | 否 |

**表 2-1　延迟预算分解与责任归属**

由表可见，**③+④（RAG 检索与 LLM 生成）是占比最大、且完全由我方掌控的环节**，是本文优化的主战场。

## 3 句子级流式驱动架构（核心设计理念）

在动手优化各段耗时之前，我们先确立了一条决定性的架构理念，它直接改变了"延迟"的定义。

**传统问答**采用"整段式"链路：等 LLM 把**整段答案**生成完毕 → 整体送入 TTS 合成 → 再驱动数字人播放。其延迟与答案长度正相关，一段两三百字的讲解往往要等待 6 秒以上才开口。

本系统采用**句子级流式（SSE）驱动**架构，如图 3-1 所示：

```
RAG 后端                         桥接层                    数字人(LiveTalking)
  │  LLM 逐 token 生成              │                            │
  ├─ 凑满一句(遇句号) ──SSE事件──▶ 订阅句子流                    │
  │    sentence: "灵山大佛高88米。" ├── /human(该句) ──────────▶ 立即合成+开口
  │  继续生成第二句…                │                            │ (不等整段)
  ├─ sentence: "它落成于…" ───────▶ 排队 ───────────────────▶ 接着说
  │  …                             │                            │
  └─ end                           │                            │
```

**图 3-1　句子级流式驱动时序**

其工程实现要点：

- **RAG 侧句子级 SSE**：LLM 输出经实时切句，每凑满一句即下发 `sentence` 事件；同时最早下发 `intent`（意图）、`emotion`（情绪）事件供前端与表情管理使用，结束时下发 `end`。
- **桥接层订阅 + 逐句驱动**：桥接层订阅该 SSE 流，每收到一句立即调用数字人 `/human` 接口驱动开口；**首句携带 `interrupt` 打断上一轮**、后续句子排队，实现"首句抢跑"。
- **真流式保障（一次关键踩坑，见 4 节注）**：必须确保 token 在异步事件循环中不被阻塞，否则会退化为"伪流式"（整段才一次性吐出），令首句抢跑失效。

> **设计理念一句话**：**采用句子级流式驱动，数字人在首句生成完成即开口，将用户感知延迟与答案总长度解耦。**

这一理念把关键指标从"整段答案生成时间（~6 s）"重定义为"**首句生成时间（~2 s）**"——后续所有优化都围绕"压缩首句延迟"展开。

## 4 瓶颈定位：埋点实测，而非主观臆断

要压缩首句延迟，必先定位它究竟耗在哪。我们没有凭直觉"猜模型慢"，而是在 SSE 流中对三个关键时间戳**埋点测量**：`intent`（检索完成）、`emotion`（首 token 到达）、`sentence`（首句完成）。

实测得到一个**反直觉的结论**：

> **瓶颈不是"首字延迟（TTFT）"，而是"生成吞吐（字/秒）"。**

具体证据：

- qwen-max 的**首字延迟 TTFT 仅约 0.8 秒**，完全正常；
- 但其**生成速度只有约 20 字/秒**，且模型倾向于用冗长的铺垫开头（如"九龙灌浴的表演时间是大家非常关心的话题……"）；
- 二者叠加，导致"又长又慢"的第一句要 2.7–7.6 秒才生成完毕。

我们进一步横向实测了候选模型的生成吞吐（见表 4-1），印证了"换更快的生成模型"是直接有效的方向：

| 模型 | 生成速度 | 首字延迟 TTFT | 流式首句耗时 |
|---|---|---|---|
| qwen-max（原） | ~20 字/s | ~0.8 s | 2.7–7.6 s |
| qwen-plus | ~48 字/s | ~0.8 s | 1.0–1.5 s |
| qwen-turbo | ~91 字/s | ~0.7 s | ~0.7 s |

**表 4-1　候选 LLM 生成吞吐对比（实测）**

> **注（伪流式踩坑）**：定位过程中曾发现一个隐性 bug——同步的 DashScope 生成器在 async 协程内被直接迭代，阻塞了 asyncio 事件循环，使 FastAPI 整段才 flush SSE（"伪流式"），连带让桥接的"首句抢跑"失效。修复方法是将同步迭代放入线程、再经 `asyncio.Queue` 把 token 异步交回。修复后首句从 8.27 s 降至 2.58 s，恢复为逐句真流式。**这印证了"先有真流式架构，逐句优化才有意义"。**

## 5 优化措施

基于上述定位，我们实施了四项优化。每项按"问题 → 原理 → 措施 → 数据"组织，关键处附踩坑说明。

### 5.1 模型选型：qwen-max → qwen-plus（数据驱动的速度/准确率权衡）

- **问题**：事实问答（qa）使用 qwen-max，生成吞吐仅 ~20 字/s，是首句延迟的根因。
- **原理**：生成吞吐是瓶颈，换用更快的模型可成倍缩短生成时间。但赛题准确率 ≥ 90% 是红线，不能盲目下沉模型。
- **措施**：在自建的 **44 题、5 景区标准测试集**上，对三个候选模型做"准确率 × 速度"联合评测，用数据决策（见表 5-1）。

| 模型 | 生成速度 | 流式首句 | 44 题准确率 |
|---|---|---|---|
| qwen-max（原） | 20 字/s | 2–3.7 s | 97.7% |
| **qwen-plus（选定）** | **48 字/s** | **1.0–1.5 s** | **100%** |
| qwen-turbo | 91 字/s | ~0.7 s | 100% |

**表 5-1　模型选型评测：准确率与速度联合对比**

- **决策理由**：qwen-plus 在保持 **100% 准确率**的同时，生成提速约一倍；qwen-turbo 虽更快，但其推理能力相对较弱，面对专家评测中的疑难题目准确率余量更小。故遵循 **"红线之上取最快"** 原则选定 qwen-plus。生成性意图（导览/推荐/共情/闲聊）则另走 qwen-turbo。
- **为何换模型而准确率不降**：这是本设计的一个关键认知——**事实由 RAG 检索到的知识库内容约束，LLM 只负责"组织语言"而非"记忆事实"**，因此小一档的生成模型同样够用。这也正是 RAG 架构相对纯参数记忆的工程价值所在。

### 5.2 Answer-first 短开口（流式架构下的提示工程）

- **问题**：即便换了模型，模型仍倾向于用冗长铺垫开头，拖慢"首句完成"这一关键节点。
- **原理**：在句子级流式架构下，**首句越短 → 越早说完 → 越早开口**，且首句越短，⑤ TTS 需要合成的音频也越短，连带受益。
- **措施**：在系统提示词中加入"开口要快"规则——**正文第一句必须简短（≤15 字、以句号结尾）并直接点出核心答案，再展开细节**；明令禁止"……真是""这个问题嘛"等冗长铺垫。
- **数据**（见表 5-2）：

| 提问 | 优化前首句 | 优化后首句 | 优化后首句内容 |
|---|---|---|---|
| 九龙灌浴几点表演 | 6.29 s | **1.89 s** | "九龙灌浴每天有四场。" |
| 门票多少钱 | — | **1.75 s** | "灵山胜境成人门票210元。" |
| 灵山大佛有多高 | 4.42 s | **1.91 s** | "灵山大佛高88米。" |

**表 5-2　Answer-first 短开口前后首句延迟对比（实测）**

- **附带收益**：把核心事实前置，**反而提升了准确率命中**——评测一上来即可见答案，无需在长段落中检索。

### 5.3 客流统计冷启动预热（消除冷启动尖峰）

- **问题**：导览/推荐类问题**首次**触发时，偶发约 **20 秒**的"假死"，而紧随其后的同类问题却很快——典型的冷启动特征。
- **原理**：导览/推荐意图会注入"实时客流"上下文，其底层数据是一份 **14 万行的 Excel**。该数据用 `lru_cache` 缓存，但**首次查询时同步加载**（openpyxl 逐格解析极慢），这次冷加载把首个请求冻住了约 20 秒。
- **措施**：① 服务启动时用**后台线程预热**该缓存，将一次性重负载从"请求路径"移到"启动路径"，等用户提问时缓存已热；② 读取时用 `usecols` 仅加载必要列，加速冷加载本身。
- **数据**：导览/推荐首句延迟从 **~20 s 冷启动尖峰 → ~1.5 s**，且预热为后台线程、不阻塞服务启动；缺少数据文件时优雅降级（导游不带客流上下文，不影响主流程）。

### 5.4 VAD 静音尾收紧（感知延迟，含权衡说明）

- **问题**：用户说完话后，VAD（语音活动检测）需等待一段持续静音才判定"一句话结束"。这段等待是纯粹的"死时间"。
- **原理**：静音保持阈值 `SILENCE_HOLD` 越短，判定越快、感知延迟越低。
- **措施**：将能量 VAD 的静音判定阈值由 **800 ms 收紧至 500 ms**，省约 0.3 s。
- **权衡（诚实声明）**：这是本组优化中**唯一有代价**的一项——阈值过短会在用户语句的自然停顿处**提前断句**（如"灵山大佛……有多高"被截断）。考虑到游客问句多为单口气短句，500 ms 是兼顾响应与容错的经验值；现场若出现误截断，可调回 650–800 ms。该参数在前端集中可配，便于演示前按现场口音/语速微调。

- **已调查、确认暂无收益的方向**：曾评估将 TTS 改为"边合成边喂"的流式以进一步压 ⑤，但经核查语音服务的 `/api/speech/tts` 为整句阻塞式合成（源头不产生渐进音频流），故该改造无收益；当前 ⑤ 已被 5.2 的短开口同步压至最小。若后续语音服务接入流式合成回调，可再行优化。

## 7 小结

本节将"语音端到端 < 5 s"从一个黑盒指标，拆解为可度量的五段流水线，确立了**句子级流式驱动**这一核心架构理念（把感知延迟与答案长度解耦），并通过**埋点实测**定位出"生成吞吐"而非"首字延迟"才是真正瓶颈这一反直觉结论。在此基础上实施四项优化——**数据驱动的模型选型、Answer-first 短开口、冷启动预热、VAD 静音尾收紧**——在**保持 100% 测试准确率**（赛题硬红线 ≥ 90%）的前提下，将事实问答首句延迟从 4.4–7.6 s（含 20 s 尖峰）降至 1.3–2.0 s，端到端预算压到约 3.5–4.5 s，稳定落在赛题"合理响应范围"示例（< 5 秒）之内并留有余量，同时消除了"长时间无响应"的稳定性隐患。
