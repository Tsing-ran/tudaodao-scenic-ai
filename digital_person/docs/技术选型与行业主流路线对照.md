# 技术选型与行业主流路线对照

本章逐模块说明系统的技术选型，并与行业主流方案和商用产品做对照，论证每一项选型为何适合景区导览数字人这一任务，以及它在当前技术路线中所处的位置。选型论证统一采用“是什么、为何适合本任务、与主流对照”的结构。

## 1. 选型总览

系统由问答核心、大模型与多模态、智能体编排、实时数字人引擎、语音、服务架构六部分组成。下表给出各部分的选型与主流参照，后续各节展开论证。

| 模块 | 本系统选型 | 行业主流 / 商用参照 | 路线判定 |
|---|---|---|---|
| 问答架构 | RAG，混合检索 + 重排序 + 查询改写 + 召回兜底 | 生产级 Hybrid RAG，检索后接重排 | 对齐生产主流 |
| 嵌入与重排 | BGE-M3 + BGE-reranker-v2-m3 | 同类开源检索/重排模型 | 对齐开源领先 |
| 向量数据库 | ChromaDB | Milvus、Qdrant、pgvector、Pinecone | 当前规模适配，可平滑替换 |
| 文本大模型 | 通义千问云端 API + 本地可插拔兜底 | 云端商业大模型为主，叠加降级 | 对齐主流，含降级容错 |
| 多模态理解 | 通义千问视觉模型，图文问答与视觉定位 | 视觉语言大模型 | 跟进多模态趋势 |
| 智能体编排 | 规则快筛 + 大模型意图分类的轻量编排 | 工具调用与多智能体编排 | 任务收敛下的成本与延迟取舍 |
| 数字人引擎 | Ditto，音频驱动运动 + 肖像形变，实时 | 实时同此路线；商用 HeyGen、D-ID；重型 3D 高斯泼溅、NeRF、MetaHuman | 实时交互档位的前沿务实选择 |
| 语音 | 云端实时 TTS；faster-whisper 识别 | 神经网络 TTS；Whisper 系识别 | 对齐主流 |
| 服务与流式 | FastAPI + 服务端推送流式；SRS + WebRTC/HLS/FLV | Python 异步服务事实标准；标准直播栈 | 对齐主流 |
| 延迟与并发 | 多级缓存 + GPU 按发话时分复用 + 答案先行 | 生产级延迟与吞吐优化 | 工程化程度较高 |

## 2. 问答核心：检索增强生成

检索增强生成是当前知识型问答的主流范式，它在生成前先从知识库检索相关材料，把事实约束在材料范围内，从而降低大模型的幻觉。

本系统没有停留在最朴素的“向量检索加生成”，而是采用生产环境常见的进阶链路：稠密向量检索与稀疏关键词检索并行，结果合并后送入重排序模型精排，查询中含指代时先做查询改写，召回为空时进入兜底策略而非强行编造。稠密检索覆盖语义相近的问法，稀疏检索覆盖景点专名、票务等关键词精确匹配，两者互补。重排序模型对候选段落做细粒度相关性打分，是把准确率推到高位的关键一环。

这条链路与业界对“进阶 RAG”的共识一致：检索召回之后必须有重排，混合检索优于单一稠密检索。在标准测试集上，系统事实性问答准确率达到 97% 量级，明显高于赛题要求的 90% 红线，验证了该链路的有效性。

嵌入与重排模型选用 BGE-M3 与 BGE-reranker-v2-m3。前者支持中英双语、在中文检索上表现领先，后者是配套的重排模型。二者均可在本地消费级显卡运行，无调用费用，且检索质量处于开源第一梯队。在启用本地 GPU 后，单次检索耗时约 0.5 秒。

向量数据库选用 ChromaDB。工业界大规模生产通常使用 Milvus、Qdrant、pgvector 或 Pinecone，它们在亿级向量与高并发下更有优势。本系统面向单景区知识库，规模在数十到数百个文本分块量级，ChromaDB 的多集合能力恰好满足多景区命名空间隔离的需求，部署轻量。由于检索层与上层问答逻辑解耦，规模化阶段替换向量库不影响业务代码，属于可平滑升级的一层。

## 3. 大模型与多模态

文本生成选用通义千问的云端稳定版模型。在中文理解与生成上，国产商业大模型处于第一梯队，通过 API 调用避免了本地部署超大模型的显存与运维成本，这也是当前中文应用的主流做法。系统同时实现了可插拔的本地大模型后端，在云端不可用时切换到本地模型兜底，对应工业界“云端为主、本地降级”的容错范式，保证问答服务在外部依赖异常时仍可用。

多模态方面，系统接入视觉语言模型处理图文问答与拍照视觉定位：游客拍摄景观，模型先识别地标确定所在位置，再由问答链路接地讲解与指路。引入视觉模态既满足了赛题对多模态大模型的要求，也契合大模型从纯文本走向多模态的整体趋势。

## 4. 智能体编排

系统在问答之上构建了一层意图编排，把游客输入分为问答、导航、推荐、共情、闲聊等类别，分流到差异化的处理逻辑。编排采用规则快筛与大模型分类结合的混合策略：明确的输入由规则零延迟命中，模糊的输入才调用轻量模型判别。

当前业界的热点是工具调用与多智能体编排，让大模型自主规划与调用工具。对景区导览这一相对收敛的任务域，过重的智能体框架会带来额外的延迟与调用成本。本系统的轻量编排在保证意图区分能力的同时，把响应延迟和成本控制在更优区间，是任务约束下的合理取舍。该层结构清晰，后续若需引入工具调用，可在现有意图处理器基础上扩展。

## 5. 实时数字人驱动引擎

数字人是本系统体验的核心，也是技术路线上要求最高的一环。技术上存在两条路线：一是重建型的三维数字人，如三维高斯泼溅、NeRF、影视级 MetaHuman，画质上限高，但通常离线渲染或依赖重型算力；二是驱动型的二维说话人，由音频驱动面部运动并对肖像做形变，在消费级显卡上即可实时。

本系统选用 Ditto 作为直播引擎，属于第二条路线。它通过音频驱动的运动扩散生成面部运动，再对源肖像做形变，本质是驱动源人物本身而非逐帧重画一张脸，因而身份、取景、神态都得到保留，整张脸协同运动，规避了只换嘴部带来的呆板观感。配合 TensorRT 推理加速，在消费级显卡上达到约 25 帧每秒的实时帧率，流式首帧约 0.7 秒，显存占用约 2.7 GB。

这一选择与商用实时数字人产品所处的技术档位一致。在“消费级算力、端到端低于 5 秒、浏览器可直接播放”的硬约束下，驱动型二维路线是当前能够落地的前沿方案。重建型三维数字人画质更优，适合作为后续阶段或更高算力场景的演进方向，已列入规划。系统同时保留了离线全脸扩散渲染能力，用于制作演示视频中的固定台词镜头，与实时直播分工互补。

## 6. 语音

语音合成采用云端实时 TTS，音色自然且不占用本地显存，可按景区切换专属音色。语音识别采用 faster-whisper，以 CPU 整型量化运行，零显存占用，把显卡完整留给数字人，并针对景区专名做了热词增强。Whisper 系模型是当前语音识别的通用主流，TTS 走云端实时接口也符合行业常规。

## 7. 服务架构与流式传输

后端采用 FastAPI，它是 Python 异步 Web 服务的事实标准，原生支持异步与服务端推送流式输出，能够边生成边下发文本。问答采用句子级流式，首句生成即可驱动数字人开口，无需等待整段生成，这是把交互延迟压到 5 秒以内的关键之一。

媒体传输采用 SRS 媒体服务器配合 WebRTC、HLS、FLV 多种协议。低延迟场景走 FLV 与 WebRTC，iOS 端走原生 HLS，按设备选择最稳的播放路径。这是直播领域的标准技术栈。

在延迟与并发上，系统设计了高频问答视频缓存、GPU 资源按发话瞬间时分复用、满载降级转文字三级机制，并对答案采用先行短开口策略。这类多级缓存与资源复用的思路对应工业界的延迟与吞吐优化实践，使单卡能够服务远多于一路会话的并发，单位成本显著低于真人讲解。

## 8. 小结

整体而言，系统的技术路线对齐工业生产主流：问答采用完整的进阶 RAG 链路，大模型走云端商业模型加本地降级，引入多模态理解，服务与媒体采用标准的异步流式与直播栈，并在延迟与稳定性上做了较深的工程化。数字人部分取实时交互档位的前沿务实方案。少数与最高端方案的差异，包括向量数据库的规模档位、智能体编排的深度、二维与三维数字人的取舍，均是在“消费级算力、实时、可落地”约束下的合理选择，且都保留了平滑升级的空间，而非技术路线上的落后。
