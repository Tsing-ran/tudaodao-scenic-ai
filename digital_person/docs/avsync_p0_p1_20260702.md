## 13. iOS27 低延迟路径现场结论

时间：2026-07-02 晚间  
原因：iOS27 真机要求数字人视频音画响应时间控制在 5s 以内，经典 HLS 更稳但延迟窗口偏大，因此手机端默认路径保持 WebRTC，HLS 仅保留为 `?player=hls` 或 WebRTC 不可用时的兜底。

当前播放策略：

- iOS/Safari 默认优先 `/rtc/v1/play/` WebRTC。
- 初始接收端 playout delay：iOS/Safari `0.65s`，其他端 `0.4s`。
- HLS playlist 路由仍保持已修复状态，作为稳定兜底。

现场日志结论：

- 114.55 SRS 日志显示 iOS WebRTC 会话可以成功建立。
- 同一会话随后出现 `NACK ARQ`、`PLI`，并出现过 `count=1092/1092` 级别的 NACK 突发。
- 判断 iOS27 卡顿/跳帧的直接原因是公网 WebRTC 路径丢包/抖动，浏览器为保持实时性进行了补包、丢帧、请求关键帧刷新。

前端文件：

- `webapp/src/hooks/useGuide.ts`

新增能力：

- WebRTC 播放后每 3s 读取一次 `RTCPeerConnection.getStats()`。
- 采集并上报：
  - video/audio packets lost
  - video/audio loss rate
  - jitter
  - frames decoded/dropped
  - freeze count
  - RTT
  - available incoming bitrate
- 上报事件类型：`webrtc_quality`，进入现有 `/rag/analytics/event`。
- 连续异常窗口时自动提升接收端缓冲：
  - 初始：`0.65s`
  - 连续异常：`1.2s`
  - 持续恶化：`1.8s`
- 该策略优先保留 WebRTC，避免直接切 HLS 导致 5s 响应目标失守。

后端文件：

- `bridge/server.py`

新增能力：

- 新增 `DRIVE_PACING`，默认开启。
- 新增 `drive_pace_wait` / `drive_pace_next` `[avsync]` 日志。
- 第一句仍立即送入 LiveTalking，保证首响不变。
- 第二句及以后按上一句估算播放时长限速送入 LiveTalking，避免 RAG 短时间产出多句后把数字人队列压爆，造成后句追前句、覆盖或体感跳句。
- 修复 `/live/say` 打断 key：
  - 旧逻辑写 `_ASK_GEN[sessionid]`。
  - 问答流实际检查 `_ASK_GEN[screen:sessionid]`。
  - 现在 `/live/say` 也写 `screen:sessionid`，迎宾/拍照讲解/直接开口才能可靠停止旧问答流。
- `/live/say` 接管旧问答槽位后会按估算说话时长释放，避免旧问答被接管后渲染槽长期占用。
